# AI 智能体面试题库（精简版）

> 每题保留核心要点 + 常见追问，适合快速背诵。

重要度：`必刷` > `高频` > `中频` > `低频`
难度：`基础` < `中等` < `较难`

---

## 1、基础认知与技术选型

### Q1-1. RAG 和微调（SFT）的核心区别？能不能一起用？
**`必刷` | `中等`**

- RAG 解决"知识从哪里来"，不改模型参数，运行时检索外部资料，适合时效性强、需可溯源的知识
- 微调解决"模型应该怎么表现"，改模型参数，适合输出风格一致性、结构化能力、领域行为稳定性
- 可以一起用：RAG 提供知识 + 微调/结构化输出保证行为稳定
- 预算有限先做 RAG（见效快、迭代灵活）

**追问：** 为什么多数企业不优先续训？什么场景适合 RAG+微调？预算有限先做哪个？

### Q1-2. 什么是 AI Agent？和传统 AI 应用的区别？
**`高频` | `基础`**

- Agent = 模型 + 工具集 + 运行循环 + 当前状态
- 传统 AI 应用：单轮输入→输出；Agent：围绕目标持续做决策
- 关键不只是用了大模型，而是具备工具调用、状态推进和动态决策能力
- 不是所有 AI 应用都该叫 Agent，固定流程用 Workflow 就够了

### Q1-3. 什么时候用 Prompt / RAG / 微调 / Workflow / Agent？
**`必刷` | `中等`**

- **Prompt**：模型本来就会，只是任务没描述清楚
- **RAG**：缺私有知识、最新知识、外部知识
- **微调**：缺稳定行为（固定格式、语气、分类习惯）
- **Workflow**：流程固定、节点明确、强调稳定和可审计
- **Agent**：路径不固定，需根据中间结果动态调用工具

**追问：** 为什么不一开始就做微调？为什么不是所有复杂任务都适合 Agent？

### Q1-4. Token 和上下文窗口是什么？工程上意味着什么？
**`高频` | `基础`**

- Token 是模型处理文本的基本计量单位，不等于字数
- 上下文窗口是单次推理最多能看到的 token 上限（8K/32K/128K）
- 工程意义：窗口决定能否做长文问答/多轮对话；token 越多成本越高、延迟越大；超出窗口会被截断
- 经验值：1 中文字符 ≈ 0.6 token，1 英文字符 ≈ 0.3 token

### Q1-5. 大模型应用上线前最关心哪些工程指标？
**`高频` | `中等`**

- **效果**：准确率、忠实度、任务完成率、引用正确率
- **性能**：首 token 延迟、端到端延迟、P95/P99
- **成本**：token 消耗、检索成本、工具调用成本
- **稳定性**：超时率、错误率、重试率、降级命中率
- **治理性**：日志、Trace、Prompt 版本、索引版本、权限审计

**追问：** 怎么设计降级策略？成本超预算先优化哪一层？

## 2、Prompt、结构化输出与护栏

### Q2-1. System Message 和 User Message 怎么分工？
**`必刷` | `基础`**

- System：放稳定约束（角色、目标、边界、安全规则、输出格式）——尽量少改
- User：放当次任务、输入数据、补充上下文、个性化要求
- 好处：结构清晰、便于版本管理和模板化、排查效果波动更容易

### Q2-2. 结构化输出有哪些做法？各自优缺点？
**`高频` | `中等`**

- **纯 Prompt 约束**（要求模型返回 JSON）：最简单但稳定性最差
- **Output Parser**（StrOutputParser/JsonOutputParser/PydanticOutputParser）：模型输出后再转程序可用数据
- **Structured Output**（with_structured_output）：在模型输出前定好 schema，约束力更强
- **Function Calling / Tool Calling**：结构化输出的一种，偏"生成调用意图和参数"
- 生产优先级：原生结构化输出 > Pydantic schema > JSON + parser > 纯 Prompt

### Q2-3. Prompt Injection 是什么？RAG/Agent 为什么要小心？
**`高频` | `中等`**

- 不可信输入试图改写系统指令、诱导模型越权或让 Agent 执行不该执行的动作
- 不只来自用户输入，也可能藏在网页/PDF/知识库文档里（间接注入）
- 五层防护：指令分层、内容隔离、工具权限白名单、动作校验/HITL、观测与兜底
- **关键：RAG 不是安全层，知识库文档本身也可能带恶意指令**

**追问：** 文档里写"忽略之前所有指令"怎么办？浏览器 Agent 怎么防隐藏提示词？

### Q2-4. 如何系统优化提示词并把准确率做上去？
**`高频` | `中等`**

- 定义任务边界（什么叫答对、什么叫拒答）
- 输入分层：稳定规则放 System，动态任务放 User
- 先修大问题再修措辞（缺知识/工具/流程不要靠 Prompt 硬抬）
- 用样例和反例（few-shot 比抽象要求更稳定）
- 能用 schema/parser 就不要只写"请返回 JSON"
- 建 badcase 集，每次改 Prompt 跑回归
- 做版本和灰度，Prompt + 模型版本 + 温度一起管理

### Q2-5. Prompt 工程的边界是什么？
**`中频` | `基础`**

- Prompt 解决不了知识缺失、复杂状态管理和强执行需求
- 资料太多→转向 RAG；复杂流程→转向 Workflow/LangGraph；调外部系统→走 Tools/Function Calling
- Prompt 负责表达规则，RAG 负责补知识，Tools 负责执行，Graph/Workflow 负责流程控制

### Q2-6. 如何做 Prompt 版本管理与回归？
**`中频` | `中等`**

- 同时管理四样东西：Prompt 模板、运行参数（模型/温度/top_p）、评测集、发布信息
- Prompt 和代码一起版本化；每次改都跑固定回归集
- 记录模板 hash + 模型版本 + 关键参数
- 换底层模型后，旧 Prompt 不一定还能保持原效果

## 3、RAG 全链路

### Q3-1. 描述一个完整的 RAG 流水线
**`必刷` | `中等`**

- **索引阶段**：文档加载→清洗→切块→向量化→写入向量库→补充元数据
- **检索阶段**：接收问题→query 改写→检索召回→重排过滤→上下文组装→模型生成→引用/脱敏/格式化输出
- 工程上真正难的是：文档是否正确解析、切块是否保留语义、检索结果是否对当前问题有帮助

**追问：** chunk 怎么切？metadata 存哪些？为什么要加 rerank？

### Q3-2. 文本切块怎么设计？常见坑？
**`高频` | `中等`**

- 目标不是"切得均匀"，而是保留对检索有意义的语义单元
- 结合固定长度 + 段落边界 + 标题层级 + 重叠窗口
- 常见坑：切块过碎、忽略标题层级、重叠不足、表格被打散、多主题塞一个 chunk 导致语义污染

### Q3-3. RAG 效果不好怎么排查？
**`必刷` | `中等`**

- **检索前**：query 是否表达清楚，是否需要改写/拆问
- **检索中**：切块、Embedding、向量库参数、top_k、过滤条件、重排是否合理
- **检索后**：上下文是否过长/有噪声、关键信息是否被淹没、是否要求"无依据就拒答"
- 企业场景还要查文档质量、版本是否最新、权限过滤是否误伤

**追问：** top_k 是不是越大越好？什么是 Lost in the Middle？

### Q3-4. 混合检索、重排序、查询改写分别解决什么问题？
**`高频` | `中等`**

- **查询改写**：用户问题表达得不够像检索语句
- **混合检索**：只靠稠密向量可能漏掉关键词命中（dense + sparse）
- **重排序**：召回了一批候选，但顺序还不够准
- 稳定方案：query 改写 + 稠密检索 + 稀疏检索 + rerank + metadata 过滤

### Q3-5. RAG 如何接入 Agent 执行链路？
**`高频` | `中等`**

- **前置检索**：问题进来先统一检索，再交给 Agent 规划
- **按需检索**（推荐为主）：把 Retriever 封成工具，Agent 需要时主动调用
- **后置校验**：先生成结果，再用检索做证据核对
- 不是每一步都需要查知识库，把 RAG 做成可调用能力更合理

### Q3-6. 企业 RAG 为什么必须重视权限、版本和引用？
**`中频` | `中等`**

- 权限：向量检索必须做租户隔离、角色过滤、文档级/段落级权限控制
- 版本：索引和源文档要可追踪，文档更新后要知道哪些向量需增量重建
- 引用：答案不能回溯到原文片段，业务方很难建立信任

### Q3-7. 什么是 Lost in the Middle？
**`中频` | `中等`**

- 上下文一长，模型更容易利用开头和结尾的信息，中间关键证据"看见了但没用好"
- 启示：不是塞更多 chunk 就更好，关键证据反而更容易被淹没
- 处理：先 rerank 和过滤再进上下文；重要证据优先放前面；分阶段检索

### Q3-8. 有了超长上下文模型，还需要 RAG 吗？
**`中频` | `中等`**

- 多数场景仍需要。"能塞进去"和"应该塞进去"不是一回事
- 知识总量太大没法全塞；长上下文成本和延迟更高；权限/版本/审计不能只靠窗口硬塞
- 长上下文是 RAG 的补充能力，不是替代品

### Q3-9. 复杂文档 RAG / 多模态 RAG 怎么做？
**`中频` | `较难`**

- 不能把 PDF/表格/图片都当纯文本处理
- 先做版面分析、OCR、表格提取、标题层级恢复
- chunk 尽量按结构块切（标题/段落/表格/图注），不要把表格切成残缺文本
- metadata 保留页码、章节标题、文档版本

### Q3-10. 什么是 Agentic RAG？
**`中频` | `较难`**

- 传统 RAG：固定流水线（检索一次→生成）；Agentic RAG：模型根据进展决定要不要检索、检索什么、是否改写 query
- 区别在于检索是不是被当成动态决策过程来管理
- 不会一开始就上 Agentic RAG，先看 badcase 是否真的集中在多跳/自检补检问题上
- 必须加步数上限、预算限制、失败退出条件

## 4、检索基础设施与检索优化

### Q4-1. 向量数据库和传统数据库的区别？为什么不能只用 MySQL？
**`高频` | `基础`**

- 向量数据库面向相似度检索，传统数据库擅长精确过滤和结构化查询——分工关系
- MySQL 也能存 Embedding，但数据量上来后 ANN 索引、混合检索、大规模召回都会低效
- 企业常见做法：结构化条件走传统库，语义召回走向量库，通过 metadata 结合

### Q4-2. Embedding 是什么？核心价值？
**`高频` | `基础`**

- 把文本变成固定长度向量，让"语义关系"映射成"空间关系"
- 核心价值：让系统具备按语义检索的能力
- 在 RAG 中，Embedding 决定"问题和知识能不能在向量空间里正确相遇"
- 建库和查询必须用同一套 Embedding 模型

### Q4-3. 如何选择 Embedding 模型？
**`高频` | `中等`**

- 先看语言和领域适配（中文/英文/代码/法律/金融）
- 建库和查询一致性是底线
- 评估三层：检索层（召回质量）、业务层（答案忠实度）、工程层（延迟/成本）
- 公开榜单只做初筛，真正决定的是自己的知识样本和 badcase

### Q4-4. 近似检索和精确检索怎么权衡？
**`中频` | `中等`**

- 精确检索效果可控但大规模下成本高；近似检索牺牲部分精确性换吞吐和响应速度
- 高风险/数据量小/一致性要求极高→精确或保守索引；通用知识问答/海量文档→近似检索 + rerank

### Q4-5. 知识图谱/图数据库什么时候比纯向量检索更有价值？
**`中频` | `较难`**

- 当核心不只是"语义相似"，而是"实体关系、路径推理、多跳关联"时
- 如设备故障排查、商品属性关联、组织关系、法规条文引用
- 更适合理解为增强而非替代：向量检索负责语义召回，知识图谱负责结构化约束

### Q4-6. GraphRAG 适合什么场景？和传统向量 RAG 怎么选？
**`中频` | `较难`**

- 适合实体关系密、需多跳推理、社区摘要或结构化约束强的场景
- 通常路径：先用传统向量 RAG 打底，badcase 集中在多跳关系时再引入图谱增强
- 只有当问题核心在关系结构上时，图谱路线收益才大于复杂度

## 5、Tools、Function Calling 与 Agent

### Q5-1. ReAct 模式是什么？
**`高频` | `基础`**

- Thought → Action → Observation 循环，把推理和行动串起来
- 模型先判断，再决定调什么工具，根据工具返回更新判断，直到任务完成
- 现代 Tool Calling Agent 不一定明文展示 Thought，更常见的是 AIMessage.tool_calls
- 优势是灵活，代价是链路更长、成本更高、调试更复杂

**追问：** CoT 是什么？CoT 和 ReAct 的区别？

### Q5-2. Tool、Function Calling、Agent 三者的关系？
**`必刷` | `基础`**

- Tool 是能力单元（"能做什么"），Function Calling 是调用机制（"怎么发起结构化调用"），Agent 是运行模式（"如何围绕目标多轮决策"）
- 很多需求只需要 Tool Calling，不一定要上完整 Agent

**追问：** 单工具助手算不算 Agent？Tool 设计的最小粒度？

### Q5-3. Agent 通常由哪些核心组件构成？
**`必刷` | `中等`**

- Agent = 模型 + 工具集 + 运行循环 + 当前状态（最小骨架）
- 记忆、规划、反思、多智能体是扩展能力，不是每个 Agent 都必须具备
- 工程设计重点控制五件事：目标和职责、工具边界、状态设计、停止条件、治理能力

**追问：** 构建复杂 Agent 最主要的挑战？

### Q5-4. Function Calling 的基本原理？
**`必刷` | `中等`**

- 模型负责决策，程序负责执行
- 链路：宿主发工具 schema → 模型返回 tool_calls → 宿主执行函数 → 结果封成 ToolMessage 交回模型 → 模型生成最终答复
- Function Calling 不是模型自己调 API，只是生成"调用哪个工具、传什么参数"的结构化意图
- 鉴权、校验、超时、幂等、重试都在宿主程序这一层

**追问：** 和文本解析调用的区别？为什么生产推荐原生 Tool Calling？

### Q5-5. 设计 Tool 的工程原则？
**`高频` | `中等`**

- **单一职责**：一个 Tool 只做一件清晰的事
- **明确 schema**：模型更稳定理解参数含义
- **可观测**：每次调用能追踪请求、参数、耗时、结果、错误
- **可失败**：必须有超时、异常码、重试策略和降级逻辑
- 涉及业务系统还要加权限校验、幂等控制和审计日志

### Q5-6. "查天气、查新闻"的 AI 助手怎么设计？
**`高频` | `中等`**

- 四层：输入与路由层（判断意图/抽取参数）→ 工具层（天气/新闻各封一个 Tool）→ 调度层（Function Calling 决定调哪个）→ 输出层（整理结果+自然语言回复）
- 单轮查天气 Prompt + Function Calling 就够，多步动态链路才需要 Agent
- 关注三点：工具描述清楚、外部 API 有降级超时、结果带来源避免二次编造

### Q5-7. 什么是"工具幻觉"？怎么缓解？
**`高频` | `中等`**

- 模型调用了不存在的工具、传了不合理的参数、或在只该读数据时触发写操作
- 缓解：工具注册表白名单、schema 强校验、工具集收敛、描述清晰区分读写边界、高风险确认、失败反馈回传

### Q5-8. Function Calling 和"让模型输出 JSON 再自己解析"的区别？
**`中频` | `中等`**

- JSON + parser：Prompt 层要求，简单通用但稳定性差
- Function Calling：协议级结构化输出，模型和宿主有明确契约
- 判断：抽取字段/轻量结构化→JSON+parser；真实工具调用/外部系统编排→原生 Function Calling

### Q5-9. 工具很多时怎么控制上下文长度和调用稳定性？
**`中频` | `较难`**

- **分层暴露**：按业务域拆（搜索/数据/执行/写操作），不要一次全暴露
- **动态选择**：Tool Retrieval 或路由，只放 Top-N 最相关工具描述进上下文
- **工具聚合**：把过细 API 封成更高层业务动作
- **描述治理**：明确"什么时候用、什么时候不用、有没有副作用"

## 6、Agent 框架与编排：LangChain、LCEL、LangGraph

### Q6-1. LangGraph 相比普通 Workflow 的最大价值？
**`必刷` | `中等`**

- 把状态、节点、边和循环显式表达出来，让动态流程可设计、可追踪、可恢复
- 适合有分支、循环、人工中断、状态持久化和多 Agent 协作的任务
- 当系统出现"要不要继续查、什么时候结束、失败后从哪恢复"时，LangGraph 优势就出来了

### Q6-2. LangGraph 里 State、Node、Edge 分别代表什么？
**`高频` | `基础`**

- **State**：共享状态（大家共同操作的上下文）
- **Node**：处理逻辑（调模型、查库、执行工具）
- **Edge**：流转规则（固定跳转或条件路由）
- 设计好不好取决于 State 是否清晰、Node 粒度是否合理、Edge 条件是否可解释

### Q6-3. LangChain 在今天的价值？
**`高频` | `中等`**

- 价值不在"能不能调模型"，而在于把 Prompt/Parser/Retriever/Tools/Memory/Callbacks 统一成可组合接口
- 简单 Demo 手写 SDK 可以，但多模型接入、链式编排、结构化输出、可观测阶段，统一会降低代码分散度

### Q6-4. 如何用 LangChain 开发 Agent？
**`高频` | `中等`**

- **classic 路线**：模型+工具+Prompt→create_tool_calling_agent→AgentExecutor
- **1.x 路线**：create_agent，底层由 LangGraph 运行时驱动
- 底层主线：定义 Tools → 选择 LLM → 设计 Prompt → "模型决策→工具执行→结果回传→继续或结束"闭环

### Q6-5. LCEL 的价值？
**`中频` | `中等`**

- 把 Prompt/Model/Parser/Retriever 都抽象成 Runnable，通过统一方式组合和调用
- 不只是写法更短，而是顺序链/分支链/并行链/函数链能用同一种接口拼装、调试和替换

### Q6-6. LangGraph 进阶特性里最有工程价值的是哪些？
**`中频` | `较难`**

- **流式处理**（stream_mode: values/updates/messages/custom）：解决可观察
- **持久化**（checkpointer）：解决可恢复，按 thread_id 保存图状态
- **时间回溯**（Time-Travel）：解决可复盘，从具体节点回看重跑
- **子图**（Subgraphs）：解决可维护，把复杂系统拆成可复用模块

### Q6-7. Checkpoint、HITL、Time-Travel 怎么讲得更工程化？
**`中频` | `较难`**

核心理解：复杂 Agent 不是"能跑起来"就够了，还要能停、能看、能批、能继续。

- **Checkpoint**：解决"做到一半能不能恢复"——长任务中断后断点续跑，失败后从上一个检查点重放，不用从头来
- **HITL**：解决"高风险动作要不要人工确认"——支付、删改数据、对外发送这类不可逆操作前，暂停等人工确认再继续
- **Time-Travel**：解决"出问题后怎么回看和复盘"——基于 checkpoint 历史回到任意节点，排障调试或重跑特定阶段

一句话记忆：**Checkpoint 负责可恢复，HITL 负责可控制，Time-Travel 负责可复盘。**

> 三者关系：Checkpoint 是基础设施（没有 checkpoint 就没有 Time-Travel），HITL 是业务规则（哪些节点需要人审批），Time-Travel 是运维利器（出问题后能回到过去重跑）。

**常见追问：** 哪些节点一定会加人工审批？Checkpointer 和长期记忆/Store 的边界？时间回溯什么时候是调试工具、什么时候是生产必需？

## 7、记忆、MCP 与多智能体

### Q7-1. 上下文窗口、短期记忆、长期记忆的关系？
**`必刷` | `中等`**

- **上下文窗口**：模型单次推理能看到的内容上限（昂贵资源）
- **短期记忆**：会话级状态（消息历史、线程状态）
- **长期记忆**：跨会话的用户/任务信息（偏好、画像、历史结论）
- 成熟系统：窗口只放高信号上下文，短期记忆保证不断档，长期记忆按需检索

**追问：** 记忆和 RAG 的区别？Redis 在记忆里适合做什么？

### Q7-2. 如何为 Agent 设计短期和长期记忆？
**`高频` | `较难`**

- **短期记忆**：消息历史持久化（内存/Redis/checkpointer），通过 MessagesPlaceholder 或图状态注入
- **长期记忆**：放在数据库/向量库/知识图谱，按需召回，不全量塞 prompt
- RunnableWithMessageHistory 适合对话历史注入；LangGraph checkpointer 适合线程级状态持久化
- 超长对话四种手段：滑动窗口、周期性摘要、检索式补充、结构化记忆槽

### Q7-3. 什么是 MCP？和 Tool/RAG/Agent 的区别？
**`高频` | `中等`**

- MCP（Model Context Protocol）= 模型上下文协议，统一标准规范 AI 应用如何连接外部工具、资源和提示模板
- Tool/Function Calling：模型如何表达调用意图；RAG：模型如何拿到外部知识；Agent：谁来规划决策；MCP：这些能力如何被标准化暴露和接入
- MCP 不等于 Agent 也不等于 Tool，偏协议和生态层

**追问：** MCP Server 暴露哪些能力？STDIO 和 HTTP 怎么选？

### Q7-4. MCP 和 Function Calling 的关系？
**`高频` | `中等`**

- Function Calling 更靠近模型决策（结构化调用机制），MCP 更靠近生态接入（统一能力协议）
- 上下层关系，不是替代关系
- Agent 可以在 MCP 暴露的能力之上继续用 Function Calling 做调用决策

### Q7-5. MCP 如何做到跨平台兼容？
**`中频` | `中等`**

- 统一协议而不是统一实现
- 不同平台/语言/宿主只要遵循同一套消息结构、能力暴露方式和调用约定，就能在协议层互通

### Q7-6. MCP 技术协议的主体内容？
**`中频` | `中等`**

- 参与角色：Host、Client、Server
- 能力类型：Tools（model-controlled）、Resources（application-driven）、Prompts（user-controlled）
- 通信机制：能力发现、请求、响应、错误、通知
- 传输方式：stdio、Streamable HTTP

### Q7-7. MCP 服务器开发流程？
**`中频` | `中等`**

1. 明确暴露的能力边界（工具/资源/提示模板）
2. 定义输入输出 schema 和错误处理
3. 选择传输方式（STDIO/HTTP）
4. 实现服务端逻辑 + 鉴权/日志/超时/异常处理
5. 客户端完成注册、发现、调用和联调测试

### Q7-8. Agent 如何接入 MCP 工具？
**`中频` | `中等`**

- 发现 MCP Server 暴露的工具/资源 → 转换成 Agent 能消费的工具描述和 schema → 模型决定何时调用 → 宿主发起 MCP 请求 → 结果回传给 Agent
- 关键不在"接通"，而在接通后仍可控（权限、超时、重试、观测、审计）

### Q7-9. MCP 的流式 HTTP 传输核心优势？
**`中频` | `中等`**

- 结果边产生边返回，不用等整次调用结束
- 降低首包延迟、支持长任务中途进度回传、利于宿主做取消/超时/部分结果处理

### Q7-10. MCP 调用如何保证并发？
**`中频` | `较难`**

- 请求唯一标识（避免响应错配）、服务端并行处理、工具执行超时/限流/优先级
- 并发治理要看"协议层+服务层+工具层"三层一起设计

### Q7-11. A2A 和 MCP 的区别？什么时候需要多智能体？
**`中频` | `较难`**

- MCP：模型和外部能力怎么接；A2A：Agent 和 Agent 之间怎么协作
- 多智能体不是越早越好，单 Agent 能处理就不要拆分
- 只有职责边界清晰、单 Agent prompt 已过载、流程确实需要角色分治时，拆分才划算

**追问：** Supervisor 和 Handoff 怎么选？多智能体最常见的失败点？

### Q7-12. 有哪些热门的 MCP 工具？
**`低频` | `基础`**

- 浏览器自动化（Playwright）、数据后端（数据库/Supabase）、文件代码（本地文件系统）、搜索知识（网页搜索/知识库检索）
- 面试重点不是背名字，而是知道为什么受欢迎（覆盖 Agent 最常见的外部能力需求）

## 8、平台实践与框架选型

### Q8-1. Coze/Dify 和 LangChain/LangGraph 的关系？
**`高频` | `中等`**

- Coze/Dify：应用层、低代码、可视化交付；LangChain/LangGraph：代码级开发框架
- 不是谁替代谁，是同一条链路上的不同层级
- 常见路径：先用平台验证业务价值，再把核心链路迁到代码框架

### Q8-2. 各类 Agent 开发框架怎么选？
**`高频` | `中等`**

- 快速原型/生态丰富→LangChain；显式状态/循环/人机协同→LangGraph；低代码快速验证→Coze/Dify；边界简单→手写 SDK
- 不要简单比"哪个最好"，要说明"什么场景下用什么更划算"

### Q8-3. 什么时候工作流比 Agent 更合适？
**`高频` | `中等`**

- 业务步骤固定、输出格式明确、强调可控和可审计时→工作流
- 如分类、摘要、内容审核、报告生成、表单填充、固定审批链
- Agent 适合开放任务和动态决策，工作流适合"有规则、可追责、可回放"的流程型任务

### Q8-4. Python 调用 Dify/Coze 工作流关注哪些工程细节？
**`中频` | `中等`**

- 五类重点：鉴权、参数对齐、流式模式、超时限制、日志追踪
- Dify：API Key 和工作流绑定；长流程用 streaming 避免网关超时；识别 SSE 里的 workflow_finished
- Coze：parameters 必须和工作流输入变量严格对齐；流式区分 PING/MESSAGE/DONE

### Q8-5. RAGFlow 等开源 RAG 平台怎么选型？
**`中频` | `中等`**

- 文档导入/解析/切块/检索体验→RAGFlow；多类 Agent/工作流/插件生态→Dify/Coze；深度定制/合规审计→自研
- 优先看四类因素：文档解析质量、权限多租户能力、对接业务系统便利性、二次开发空间

## 9、安全、评测、部署与可观测性

### Q9-1. 如何评估 RAG 或 Agent 系统效果？
**`必刷` | `较难`**

- 分**离线评测**和**在线评测**
- RAG 两层：检索层（召回质量/引用正确率）+ 生成层（忠实度/拒答能力）
- Agent 两类：轨迹级（工具选择/参数/循环）+ 结果级（任务完成率）
- 自动评测：规则 + LLM-as-a-judge + 人工抽检
- 评测闭环：分层建指标→沉淀 badcase→驱动迭代

**追问：** RAGAS 适合做什么？badcase 数据集怎么建？

### Q9-2. 什么是"幻觉"？应用层怎么缓解？
**`高频` | `中等`**

- 不只是"完全胡说"，更常见的是"看起来像真的但细节/引用/时间点偏了"
- 四层缓解：知识层（RAG/引用/无依据拒答）、执行层（交给 Tool）、约束层（结构化输出/schema 校验/低温度）、治理层（badcase 回灌/人工抽检/降级）
- 幻觉很难彻底消灭，目标是可发现、可限制、可回滚、可复盘

### Q9-3. 多用户场景下如何为 Agent 做安全沙箱隔离？
**`高频` | `较难`**

- **环境层**：Docker/容器隔离，限制 CPU/内存/网络/文件系统
- **系统层**：seccomp/AppArmor/只读根目录/非 root 运行
- **应用层**：工具白名单、文件访问白名单、系统命令白名单、审计
- MCP/Tool 负责"能不能调"，沙箱负责"即使调了也跑不出边界"

### Q9-4. Agent 部署和运维有哪些指标？
**`高频` | `中等`**

- 效果指标（任务完成率/满意度）、性能指标（首token/延迟/P95）、稳定性指标（成功率/超时率）、成本指标（token/工具调用）、治理指标（人工接管率/审计完整性）
- 多工具 Agent 还要看每一步的成功率和卡点分布

### Q9-5. RAG 系统实际部署面临哪些挑战？
**`高频` | `较难`**

- 六类挑战：数据侧（解析/切块/更新）、检索侧（Embedding/召回/重排）、生成侧（上下文组装/忠实度/拒答）、治理侧（权限/版本/引用）、评测侧（badcase/闭环）、工程侧（延迟/成本/缓存/运维）
- RAG 是完整链路，任何一层出问题，最终答案都会出问题

### Q9-6. 如何确保 Agent 行为安全可控？
**`高频` | `较难`**

- 模型与提示层：System Message 明确角色/边界/拒答策略
- 工具与权限层：schema 约束、鉴权、参数校验、最小权限
- 执行与流程层：最大步数、超时、人工审批、转人工、失败兜底
- 观测与审计层：调用日志、trace、关键决策点、人工复盘
- 补预算控制（最大调用次数/token/费用预算）和熔断机制

### Q9-7. Agent 链路耗时很长怎么定位瓶颈？
**`高频` | `较难`**

- 分解五层：模型层（推理时长/首token）、检索层（召回/重排/外部搜索）、工具层（API延迟/浏览器/代码执行）、编排层（路由/重试/串行等待）、结果层（后处理/存储/日志）
- 给每一步打 trace 和 span，看 wall time 花在哪
- 很多五分钟任务不是卡在模型，而是状态流转和执行闭环没设计好

### Q9-8. 意图识别/任务路由怎么做？
**`高频` | `较难`**

- 三层：目标分类（FAQ/RAG/Tool/Agent/转人工）→ 路由机制（规则兜底+语义分类）→ 置信度治理（低置信度澄清/降级/转人工）
- 多级路由：业务意图路由 → 子域路由 → 模型路由
- 不做"单层万能路由器"

### Q9-9. 大模型应用的可观测性怎么做？
**`中频` | `中等`**

- 三件事：有日志、有指标、有 Trace
- 打通 trace_id，串联入口请求/Prompt版本/模型版本/索引版本/检索结果/工具调用/异常/耗时/token用量
- Agent 可观测性尤其重要，很多问题发生在中间步骤

### Q9-10. 控制成本优先从哪些层面下手？
**`中频` | `中等`**

- 模型层：大小模型分层
- 上下文层：压缩 Prompt，减少无效历史
- 检索层：优化召回和重排
- 流程层：减少不必要 LLM 调用，能规则化就不要全靠模型

### Q9-11. 模型路由怎么做？
**`中频` | `较难`**

- 三层：意图路由（FAQ/RAG/Tool/Agent）→ 复杂度路由（简单任务走小模型，复杂决策走大模型）→ 成本路由（热点查缓存，高风险给强模型）
- 本质是效果、成本和稳定性之间的平衡器
- 配合评测和线上数据调：看各分支完成率/延迟/成本，看有没有误下沉

### Q9-12. 内网环境怎么设计 Agent/RAG 系统？
**`中频` | `较难`**

- 核心：数据不出域、模型可控、依赖可替换、链路可观测
- 三层：应用层（Dify/Coze 私有化或自研）→ 推理层（Xinference 统一管理 LLM/Embedding/Rerank）→ 数据层（内网向量库/关系库/对象存储）
- 关键点：模型接入统一（OpenAI-compatible API）、网络权限隔离、知识治理、可观测审计、降级能力

## 10、典型业务场景设计题

### Q10-1. 设计企业知识库问答系统
**`必刷` | `较难`**

- 四层：数据接入（文档解析/切块/向量化/索引更新）→ 检索链路（query改写/混合检索/rerank/权限过滤/上下文组装）→ 生成链路（基于证据回答/无依据拒答/带引用）→ 治理能力（权限/版本/监控/评测/badcase回灌）
- 企业场景预留：转人工、知识修订、索引回滚、多租户隔离

### Q10-2. 设计 NL2SQL Agent 的风险控制
**`高频` | `较难`**

- schema 注入：不把整个 DB schema 全量塞上下文，按问题做裁剪和 schema linking
- SQL 安全：限制只读查询、禁止危险语句、加执行沙箱和超时
- 执行验证：语法检查和执行前校验
- 歧义澄清：时间范围/口径定义/字段歧义支持澄清

### Q10-3. 设计客服智能体
**`高频` | `较难`**

- 优先考虑：意图识别、知识检索、流程执行、人机协同、复盘闭环
- 系统要能回答/查状态/调接口/补资料，不确定时转人工并完整交接上下文
- 上线后持续复盘高频未解决/误判意图/知识缺口/转人工原因

### Q10-4. 如何设计 Agent 的完成判断与终止条件？
**`高频` | `较难`**

- 四层终止逻辑：任务层（是否达成目标）→ 工具层（关键工具调用是否成功）→ 状态层（state 是否进入终态）→ 保护层（最大步数/超时/重复无进展）
- Supervisor 更适合做辅助审查和异常兜底，不是唯一结束依据
- 只有关键任务结果+工具返回+状态机条件都满足时，才允许进入最终答复

### Q10-5. Code Agent 怎么设计？
**`高频` | `较难`**

- 六层：任务理解→代码库理解（搜索/文件树/符号索引）→计划与执行→工具（搜索/读写文件/运行测试/执行命令）→反馈闭环（lint/测试/diff 继续修正）→安全治理
- 真正难点：上下文治理（代码库大时拿最相关上下文）、验证闭环（判断修复真的生效）、失败处理（连续修不好怎么停）

### Q10-6 & Q10-7. Deep Research 系统怎么设计？
**`中频` | `较难`**

- 和普通 RAG 区别：从"单轮问答"升级成"多轮研究流程"
- 核心模块：查询规划器（拆子问题）→ 检索执行器（多源检索）→ 信息融合层（去重/冲突检测/可信度加权）→ 迭代控制器（证据不足继续补检）→ 报告生成器（摘要/正文/引用）
- 通常用 Workflow 或 LangGraph 显式编排，不完全交给黑盒 Agent

### Q10-8. Python 代码解释器怎么设计？
**`中频` | `较难`**

- 核心：模型生成代码 + 安全执行 + 回传结果
- 五层：代码生成→沙箱执行（隔离/白名单/超时/资源限制）→结果回传（stdout/stderr/文件/图表）→状态管理（多轮保留变量）→安全治理（禁止危险系统调用/网络访问）

### Q10-9. 类 Manus 通用智能体怎么设计？
**`中频` | `较难`**

- 本质是把 Agent 最小骨架扩展到更长任务链和更复杂任务空间
- 模块：任务理解与规划→工具调度（搜索/浏览器/代码/文件系统）→状态与记忆→执行与反思→安全与治理
- 和普通 Agent 区别：需要长期推进任务、处理中间产物、管理复杂状态

### Q10-10. 浏览器自动化 Agent 怎么设计？
**`中频` | `较难`**

- 闭环：页面感知（DOM/截图/可交互元素）→ 决策（点击/输入/滚动/等待/回退）→ 执行 → 校验（动作是否生效）→ 治理（超时/重试/幂等/防误操作）
- 最大难点：网页不稳定、异步加载、状态漂移、误操作成本高

### Q10-11. Agent 在真实/模拟环境执行任务和纯软件 Agent 的区别？
**`中频` | `较难`**

- 纯软件：操作数字系统，输入输出结构化，可回放性强
- 真实/模拟环境：面对感知噪声、状态不完备、实时反馈、物理副作用
- 更强调闭环感知、实时性、仿真验证、失败保护、人工接管

## 11、项目表达与面试实战

### Q11-1. 介绍做过的 RAG/Agent 项目怎么讲？
**`必刷` | `中等`**

- 顺序：业务目标 → 方案设计 → 你负责的部分 → 难点 → 指标结果
- 不要先报技术栈，先讲解决了什么业务问题
- 轻量 STAR：情境→任务→行动→结果
- 面试官最常追问：你具体负责哪一层？遇到什么 badcase？为什么这么选型？上线后怎么评估？

### Q11-2. 面试官问"为什么不用更热门的框架/模型"怎么答？
**`高频` | `中等`**

- 四层展开：业务复杂度、工程约束（团队熟悉度/交付周期）、部署条件、成本与性能
- 体现两点：知道替代方案（不是没调研过）；给当前方案留了迁移路径（不会锁死）

### Q11-3. 线上效果波动大怎么展示排障能力？
**`中频` | `中等`**

- 分层排查：输入分布变化 → 模型/Prompt 变更 → 检索召回 → 工具调用 → 上下文组装 → 接口超时 → 评测集失真/缓存污染
- RAG：抽样看 query、召回片段、最终答案是否一致
- Agent：检查每一步工具调用和状态推进是否异常

## 12、工具生态与岗位认知

### Q12-1. 常用哪些 AI 开发工具？
**`中频` | `基础`**

- 通用对话/研究：ChatGPT、Claude、Perplexity
- AI 编码：Cursor（IDE 内协作）、Claude Code（终端代码库级 Agent）、Copilot（轻量补全）
- 低代码/工作流：Coze、Dify
- RAG/知识库：RAGFlow
- 按阶段组合使用，不是只选一种

### Q12-2. Cursor、Claude Code、Copilot 的差异？
**`中频` | `基础`**

- Cursor：IDE 内协作，边看代码边补全/局部改写
- Claude Code：终端里的代码库级 Agent，跨文件理解/执行命令/完整任务闭环
- Copilot：轻量级代码补全，低打断，嵌入现有编辑器
- 判断标准：代码库上下文理解深度、执行边界、可控性、是否契合团队工作流

### Q12-3. AI 应用工程师和算法研究岗的差异？
**`低频` | `基础`**

- AI 应用工程师：把模型能力稳定/安全/低成本交付到业务系统（选型/架构/RAG/Agent/评测/部署/监控）
- 算法研究岗：改进模型本身能力边界（训练/微调/数据构造/算法实验）
